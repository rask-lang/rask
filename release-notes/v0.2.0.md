# Rask v0.2.0

Two things make this release: the downloaded binary can compile a program now,
and the compiler stopped leaking memory almost everywhere it used to.

## The binary works

`v0.1.1`'s didn't. The compiler links a C runtime, and it found that runtime by
walking up from its own path looking for `compiler/runtime/` — a directory that
exists in a git checkout and nowhere else. So on a downloaded `rask`:

```
error: link: Could not find runtime directory — set RASK_RUNTIME_DIR to the
directory containing runtime.c
```

Everything that doesn't link worked (`--interp`, `check`, `fmt`); everything
that does — `run`, `build`, `compile`, `test` — did not. The runtime sources now
travel inside the binary and are unpacked to a cache on first use. A checkout on
disk still wins, so editing `runtime/*.c` takes effect on the next compile
without rebuilding the compiler.

`rask --version` also reports the right version now. It said `0.1.0` under the
`v0.1.1` tag, because the tag and the workspace version were never connected.

## Memory

A leak gate runs every program in the suite under leak checking and fails the
build on a new one. When it started reporting honestly it found **173 leaking
programs**. It's now **31, holding 86 allocations, out of 502** — and the
remaining ones are individually described in `tests/known_leaks.txt` rather than
being a pile.

Worth knowing why that number was ever hidden: the gate decided by grepping the
output of `rask test`, and `rask test` was reading the test binary's stderr and
throwing it away. The report never reached the grep, so every file read as
clean. A gate that reports the expected answer without testing anything is worse
than no gate.

Most of what got fixed was one question asked in a dozen places: *when a value
moves into or out of a struct, a container, or a closure, who frees it?*
Containers in struct fields, containers captured by closures, module-level
constants, values handed back through a call inside an optional or an error
union, boxed errors, closure environments — each needed its own answer. That
last one is only half done: when the callee gets inlined there is no call left
to read the handoff from, and the container still leaks ([#1117]).

## Also in this release

- **Multi-package builds.** `rask build` across a package boundary had no test
  coverage and did not work. Every package parsed its files starting its node
  counter at zero, so two unrelated expressions in two packages carried the same
  id and the checker's record of one was read as the other's — a `Vec<i64>` came
  back typed `i64`. There are 15 fixture builds and a gate now.
- **Subprocesses run natively.** `os.Command` was interpreter-only.
- **Ranges have methods.** `(1..5).sum()`, `.map()`, `.to_vec()` — a range used
  to support nothing but `for`.
- **Eleven declared Vec/Map methods now exist.** They type-checked and did
  nothing before.
- **The C surface works both ways.** A struct from an `import c` header can be
  built and passed by value, and `to_cstring()` is real, so a Rask string can
  reach a C `const char*`.
- **Struct fields hold their declared width.** A `u8` field used to be read as
  eight bytes, taking the seven after it with it. A `Vec<Rgba>` is 4 MB now
  rather than 32.
- **Panics.** `ensure` blocks run, and a panicking program exits 101 instead of
  aborting.
- Over 200 issues closed since `v0.1.1`.

## Where it stands

All five validation programs compile and run natively: an HTTP JSON API server,
a grep clone, a game loop with entities, a text editor with undo, and an
embedded sensor processor. Each is in a gate with its output compared across
both backends, so this is measured on every push rather than claimed here.

- 141 specs, 30 stdlib modules, 505 test programs.
- **Twelve CI gates.** The interpreter and the native (Cranelift) backend are run
  against each other on every test program: **500 agree, 5 are registered red**
  with an issue each. The language guide is compiled too, so a chapter whose code
  stops working fails the build rather than quietly going stale.

## Known gaps

- **The sequence protocol isn't finished** ([#1046]). Adapters over `Vec.iter()`
  work — `filter`, `map`, `take`, `fold`, `enumerate`, `flat_map` — but
  `Vec.iter()` doesn't yet return a real `Sequence`, so the general protocol
  can't land.
- **Some callable values aren't callable.** A closure stored in a `Map` ([#1151])
  or held in a struct field ([#1152]) can't be called. #1151 is the worse one —
  making it compile gives a wrong answer.
- **31 programs still leak** ([#1035], [#1117], [#1154], [#1139] and others), and
  a task killed by a panic doesn't unwind its captures. A container returned
  inside a `T?` or `T or E` from a callee small enough to be inlined is the
  `cstring` case ([#1117]) — worth knowing if you hit it, since it's the one
  wrapper shape that isn't covered.
- **No SIMD below the type checker** ([#1059]); `@binary` parses and builds on
  the interpreter but generates no native methods.
- **`Shared.staged()`** doesn't run on either backend in its bare form
  ([#1156], [#1157]).
- Cross-compilation configures a target but needs a C cross-linker. `--target`
  and `rask targets` work; the wider toolchain doesn't.
- Incremental compilation is designed, not built.

## Platforms

Linux x86_64 and macOS aarch64. Both need a C compiler on the machine — the
runtime is compiled and linked locally, which is also why its sources ship
inside the binary.

## On the commit range

`v0.1.1` shares no ancestry with this release; the history was replaced between
them. GitHub's compare view for the two tags is not a diff of this release, and
a generated commit list would be every commit on `main` rather than the new
ones.
