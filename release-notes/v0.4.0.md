# Rask v0.4.0

One theme: a value works in every position. The deliverable was never a bug fix
— it was a grid. Every payload kind in every carrier, one small program per
cell, run on both backends, so the holes get found by enumeration instead of one
report at a time.

`tests/matrix/run.sh` reports **281 of 283 cells clean**, 2 registered red, 0
new. That's the gate, and it's green.

## The matrix

18 payload kinds — the primitives, `struct`, `enum`, `Vec`, `Map`, tuple,
closure, function reference, `Shared`, `Heap`, `Sequence` — crossed with 16
carriers, among them a struct field, a `Vec` element, a `Map` value, the success
side of a `T or E`, a closure capture, a `Shared` box, a `Heap` box, and a value
yielded out of a sequence.

These read as unrelated bugs and aren't. A closure works as a local and not out
of a `Map`. A function works as an argument and not as a struct field. Nothing
had ever enumerated value-kind × position, so each hole arrived on its own as a
separate mystery.

Ten bugs across 25 cells on the grid's first full run. All fixed; some of the shapes:

- `Heap(expr)` never allocated — the box local held the payload directly, so a
  float truncated and a container segfaulted ([#1234]).
- A struct or enum passed into a closure parameter came back as garbage
  ([#1235]) — right about one run in forty, which is why it had survived.
- A closure out of a `Map` couldn't be called, and making it compile gave a
  wrong answer ([#1151]).
- MIR gave up on a function value held in an optional or a `Map` ([#1239]).
- An f32 yielded through a `Sequence` read back as 0 ([#1243]).

Plus [#1236], [#1237], [#1238], [#1240], [#1241], [#1242], and two the matrix
doesn't reach but shares a theme with: a string field assigned through an inline
lock chain ([#1232]) and a closure in a struct field leaking once the struct is
a `Vec` element ([#1228]).

The grid is not a one-off. `tests/matrix/known_red.txt` holds each red cell to
what it claims — which backend fails it, and how far that backend gets — the
same discipline the differential harness applies to a suite file. A cell
registered for a codegen bug that stops type-checking for an unrelated reason is
red either way, and the bug quietly stops being exercised; the gate calls that
MISFILED. A registered cell that starts passing is reported so the line gets
pruned.

**Read the cell count against v0.3.0's with care.** It was 284 of 286 while
`Vec<Heap<T>>` still compiled. Enforcing `std.collections/C4` ([#1245]) turned
three of those cells from "should be rejected and isn't" into pairs that aren't
legal Rask, so they moved to the generator's skip list with the rule written
next to them. Fewer cells, one more enforced rule.

## Sequences are finished

[#1046] was filed as "the adapters wait for `Vec.iter()` to return a
`Sequence`". It closed by going the other way: `.iter()` is gone. A collection
is its own chain head, so `v.filter(p)` and `for x in v` are the spellings and
there is no second call whose return type needs changing.

```rask
let long: Vec<string> = words.filter(|w| w.len() > 4u64).to_vec()
```

`v.filter(p)` hands back a `Sequence<T>` now rather than a second `Vec`, and
fusion is untouched — that chain is the same index loop with no heap closure it
always was. Routing it through the sequence machinery instead would cost three
heap closures per stage, which is 26ms where the fused form is a few.

A plain closure is a `Sequence<T>`, so writing your own source takes no type and
no constructor:

```rask
func count_to_three() -> Sequence<i32> {
    return |yield| {
        if !yield(1) { return }
        if !yield(2) { return }
        if !yield(3) { return }
    }
}
```

The last thing under that issue was a value failing in a position, which is why
it belonged to this milestone. `for w in words.as_sequence() { w.len() }` died
in lowering with "method `len` on receiver of unresolved type". MIR knew a
`Sequence<T>` holds `T`; the checker didn't — it special-cased `Iterator` and
`Range` and let `Sequence` fall through to "the element type isn't readable from
here" — so the loop variable kept a free type variable and dispatch had nothing
to name.

## Pool is gone

`Pool` and `Handle` are deleted, along with everything that existed to serve
them: 18,000 lines deleted against 1,700 added, across the corpus, the compiler
and the specs ([#908]). Racks and links replaced them everywhere, and the useful consequence
is that the language now has **no signature coloring at all** — `using Pool` was
the last thing that made a function's signature depend on what it reached for.

## Thirty other fixes

[#1298] took thirty issues off the list in one batch. The largest was giving MIR
a type that says "closure", which was the shared root cause behind three leaks
and one silent wrong answer. Also in there: `try` was only rejected when the
enclosing function returned `void`, so a plain `i64` return slipped through and
native printed garbage ([#1251]); `result ?? value` still compiled, which let an
error be dropped without the source saying so ([#1250]); `--target
aarch64-macos` silently emitted an ELF object ([#1185]); and a task that joined
another deadlocked when every worker was blocked in join ([#1130]).

One of those thirty was closed without being fixed — [#1244], a function type on
the success side of `T or E`, which needs a ruling rather than a patch. Its
repro still fails and it's open again. Its two cells are the 2 red above.

## Cross-package conformance

The orphan-rule question is settled and written into `type.generics` as XC1–XC6
([#312]). Within a package, two `extend T with Trait` blocks for the same pair
used to pick the last one silently; that's an error now.
