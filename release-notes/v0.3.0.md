# Rask v0.3.0

One theme: memory is settled. The leak gate went from **31 programs holding 86
allocations** to **zero**, and the half of the question it never asked — memory
given back too early rather than not at all — has a gate of its own now.

## Leaks

`tests/leak_gate.sh` runs every program in the suite under leak checking and
fails on a new one. At v0.2.0 it reported 31 files leaking 86 allocations out of
502. It now reports **521 of 525 clean, 0 allocations**, and
`tests/known_leaks.txt` is one line — a `Shared` box the clone-elision pass
can't yet tell apart from the caller's own, so freeing it would be a double free
rather than a smaller leak. That one is measured, held to its count, and
deliberately not judged against a memory milestone, because a memory milestone
can't fix it.

Most of what got fixed was one question asked in places nobody had asked it:
*who frees this*. Some of the shapes:

- A value that hands its old version into its new one, freed by nobody
  ([#1213]) — a `Chain.More(Node { next: Heap(out) })` where `out` is the name
  the loop reassigns.
- A task's closure allocation, freed on the line after the body's own call —
  which a panicking body longjmps straight past ([#1223]). `TaskHandle.join`
  read as returning a view into its receiver at the same time, so the frame
  released nothing it got back either.
- A variable an `ensure` body names becomes a memory slot, because the hook
  holds its address for a panic that may come long after the frame stopped.
  Nothing freed what those slots held: `ensure v.push(2)` leaked the vector
  ([#1224]).
- A user function named `string_shoutify` read as an internal spelling of the
  `string` family, so what it handed back was released by nobody — a leak in
  someone's program caused by what they named their function ([#1217]).

Twenty-eight issues closed since v0.2.0 across 123 commits.

## The other direction

A leak is the polite version of getting *who frees this* wrong. Giving memory
back too early, or reading a field nobody wrote, is the same confusion pointed
the other way — and nothing measured it. No valgrind, no sanitiser, in any of
the thirteen gates or in CI. Every use-after-free found until now was found by a
crash.

`tests/memcheck_gate.sh` runs the same suite binaries under valgrind's memcheck.
Within a minute of first being pointed at the suite it found a live bug in
week-old code: a pool built field by field that had grown two fields nobody
initialised, which the leak gate, twelve other gates, CI and a 30× poisoned
stack run had all called green. It reports **522 clean, 0 findings**, and runs
in CI beside the leak gate.

The fix for that class is structural rather than a patch: thirty-six
constructors across the C runtime now build their struct whole, so C99
zero-fills anything the literal doesn't name. "Forgot a field" stops being
possible — there is only "meant zero".

## Linearity

`mem.linear/L1–L6` says a linear value is consumed exactly once, and the
implementation is a set of checks at particular syntactic points. The holes were
wherever a point was missed. An audit of the grid — where an obligation can be
created, where control can leave a scope, every way a value can be consumed —
ran four passes over roughly seventy cells and found six holes: `break`,
`continue`, a `try` between acquiring and consuming, a resource bound out of a
`catch` fallback, a resource stored in a struct field, and a channel whose ends
were linear because of what they carried.

Not one was a wrong rule. Every one was a point nobody had put on the list. New
error `E0881` covers the `try` case, pointing at where the resource was
acquired.

## Known gaps

- **A resource crossing a task boundary when the task panics** ([#882], [#299]).
  Captures aren't unwound at all yet; that's v0.5's theme.
- **One rare double free** ([#1218]) in a tutorial with two `own` tasks over one
  `Shared`. Seen once. Not reproduced in 960 runs under load, 30 under
  memcheck with fair scheduling, or by helgrind and DRD — the write-up on the
  issue records what each of those rules out.
- **A user function named exactly like a stdlib method's internal spelling**
  ([#1227]) is dispatched to the stdlib one. `func string_pad(s: string)` fails
  to compile with a Cranelift arity error; a same-arity collision would call the
  wrong function silently.
- **Some callable values aren't callable** ([#1151], [#1152]) — a closure in a
  `Map` or a struct field. #1151 is the worse one: making it compile gives a
  wrong answer. This is v0.4's theme.
- **The sequence protocol isn't finished** ([#1046]). The adapters work;
  `Vec.iter()` doesn't yet return a real `Sequence`.
- **No SIMD below the type checker** ([#1059]).
- Cross-compilation configures a target but needs a C cross-linker. Incremental
  compilation is designed, not built.

## Platforms

Linux x86_64 and macOS aarch64. Both need a C compiler on the machine — the
runtime is compiled and linked locally, which is why its sources ship inside the
binary.
