Learning Rask

What Rask is

A systems language built around one bet: if references can’t be stored, lifetime annotations stop being necessary.

Borrow a value for a call or an expression and it works the way you’d expect. Put the borrow in a struct field, or return it, and there’s no syntax for what you’re asking — which is the point. Nothing outlives the thing it points at, so there’s nothing to track, and signatures carry types and nothing else.

Graphs need stored references, so exactly one kind exists: a Link into a Rack. The rack owns every node and outlives every link into it, so even that one has no lifetime to name.

Somewhere between Rust and Go. Closer to Rust on safety, closer to Go on ceremony.

import fs
import io

func grep(path: string, pat: string) -> void or io.IoError {
    mut file = try fs.open(path)
    ensure file.close()

    let text = try file.read_text()
    for line in text.lines() {
        if line.contains(pat) { println(line) }
    }
}

Three rules meet in those eight lines. fs.open hands back a linear resource the compiler makes you consume exactly once. ensure defers that consumption to the end of the scope. try returns early on failure — and because the consumption is already scheduled, leaving early still closes the file. No defer discipline to remember, no destructor running out of sight.

Already writing Rask. The language card is the whole language on one page for looking a rule up. The example programs are complete and CI-checked. The specs are the normative wording when the other two disagree.

Here for the design. The blog is the long-form argument; CORE_DESIGN.md is the principles it falls out of, and RULINGS.md is how open questions get settled.

Try it in the browser

The playground runs Rask without installing anything. It’s the interpreter compiled to WebAssembly, so the code runs in your browser rather than on a server.

Open the playground →

Write code on the left, Ctrl+Enter to run, output on the right. Run tests runs the file’s test blocks instead of main. The examples dropdown loads the programs from examples/, and Copy link gives you a URL with your code in it.

What it can’t do

A browser has no files, no sockets, no clock and no threads, so anything needing one of those is refused with a message rather than half-working:
fs, io, net, httpno filesystem or sockets
timeno clock — which is also why benchmark blocks don’t run here
spawn { }, Thread.spawn { }, ThreadPool.spawn { }, using Multitasking, using ThreadPoolno threads
extern "C", import cno libc to call

Everything else runs: collections, structs, enums, generics, interfaces, pattern matching, closures, error handling, comptime. Recursion is capped a few hundred frames deep, because the browser puts a much lower ceiling on call depth than an OS thread does.

The dropdown only lists examples that actually run here. The rest are in examples/; to run those, install Rask and run the file directly.

Install it

Rask is young and changes between releases. Expect breaking changes.

The one line

curl -fsSL https://rask-lang.dev/install.sh | sh

That downloads the latest release’s rask binary for your machine into ~/.local/bin. Releases have binaries for Linux on x86_64 and macOS on Apple silicon; on anything else the script says so and stops, and you build from source (below). It doesn’t touch anything else, so uninstalling is deleting ~/.local/bin/rask.

Two things it checks for and tells you about:

  • ~/.local/bin on your PATH. If it isn’t, the script prints the line to add to your shell’s startup file.
  • A C compiler. rask run compiles your program to machine code, and the last step, linking, uses the system’s cc. Without one only the interpreter works (rask run --interp). On macOS, xcode-select --install gets you one; on Linux, your package manager’s gcc.

Check it worked:

rask --version

To pick a release other than the latest, or install somewhere else, set RASK_VERSION or RASK_INSTALL_DIR for the sh:

curl -fsSL https://rask-lang.dev/install.sh | RASK_VERSION=0.6.0 sh

The script itself is docs/install.sh if you’d rather read it first.

Build from source

You need Rust (from rustup.rs), git and a C compiler.

git clone https://github.com/rask-lang/rask
cd rask/compiler
cargo build --release -p rask-cli

The binary is compiler/target/release/rask. Put that directory on your PATH, or copy the file to ~/.local/bin.

A function says what it takes and what it gives back. It gives the value back with return, every time: the last line of a function is not returned on its own, the way it is in Rust or Ruby.

Names that change

A let name holds its value for good. A name whose value changes is made with mut. You have to pick, so when you read let you know the value stays put for the rest of the block.

func total(a: i32, b: i32, c: i32) -> i32 {
    let sum = a
    sum += b
    sum += c
    return sum
}

test "total" {
    assert total(1, 2, 3) == 6

if and else

The condition needs no parentheses. The block after it always has braces, even when it’s one line.

func abs(n: i32) -> i32 {
    if n < 0 {
        return -n
    }
    return n
}

if also gives a value. When each side is a single expression, write it after a colon instead of a block:

let kind = if n % 2 == 0: "even" else: "odd"

while

while repeats its block as long as the condition holds. Parameters are let names, so a function that counts something down copies the value into a mut name first.

func halvings(n: i32) -> i32 {
    mut left = n
    mut steps = 0
    while left > 1 {
        left = left / 2
        steps += 1
    }
    return steps
}

Integer division drops the remainder: 7 / 2 == 3.

Vec

A Vec is a list that can grow. Vec.from([...]) makes one from values, Vec.new() makes an empty one, push adds to the end, len() counts, and v[0] is the first item. Pushing changes the list, so it needs a mut name.

func countdown(from: i32) -> Vec<i32> {
    mut list = Vec.new()
    mut n = from
    while n > 0 {
        list.push(n)
        n -= 1
    }
    return list
}

A Vec can’t go straight into a string, because there’s no one right way to show a list to a user. "{list:debug}" shows it the way a programmer wants to see it, [3, 2, 1].

Structs

A struct groups a few values that belong together into one type of your own. A point on a map is an x and a y; passing them around as two loose integers invites mixing them up, while a Point keeps them together and names them.

You build one like a function call, giving every field by name, and read a field with a dot: p.x.

struct Point {
    x: i32
    y: i32
}

func distance_from_origin(p: Point) -> i32 {
    return abs(p.x) + abs(p.y)
}

func abs(n: i32) -> i32 {
    return if n < 0: -n else: n
}

Changing a struct in place comes later. For now, a function that “moves” a point builds a new one from the old one’s fields.

Methods

A function that belongs to a type is called a method, and methods go in an extend block for that type. A method that takes self is called on a value, p.flipped(), and self is that value. One without self is called on the type itself, Point.origin(), and is usually a way to build one.

struct Point {
    x: i32
    y: i32
}

extend Point {
    func origin() -> Point {
        return Point(x: 0, y: 0)
    }

    func flipped(self) -> Point {
        return Point(x: self.y, y: self.x)
    }

    // Your turn: `a.plus(b)` adds the two points field by field.

    assert p.y == 1

test "plus" {

Enums and match

An enum is a type whose value is one choice from a fixed list. A direction is North, East, South or West and nothing else.

You could use a string for that, “north”, but then “nrth” is a direction too, and nothing tells you which strings are allowed. With an enum the list is written down once, the compiler rejects anything not on it, and a reader sees every possibility in one place.

match is how you act on an enum, and you’ll see it everywhere in Rask. It picks the arm for the value it has and must cover every case: leave one out and the program doesn’t compile. So when you add a fifth case to an enum, the compiler shows you every match that has to handle it. Like if, match gives a value.

enum Direction {
    North
    East
    South
    West
}

func opposite(d: Direction) -> Direction {
    return match d {
        Direction.North => Direction.South,
        Direction.East => Direction.West,
        Direction.South => Direction.North,
        Direction.West => Direction.East,
    }
}

Your turn: turn_right gives the direction a quarter turn clockwise, so North becomes East.

    assert opposite(Direction.North) == Direction.South
}

    assert turn_right(Direction.North) == Direction.East
    assert turn_right(Direction.West) == Direction.North

Enums that carry data

Each case of an enum can carry its own fields, and each case can carry different ones. A card payment has a fee; cash doesn’t; a free order has no amount at all. A struct would need every field for every case, with some of them meaningless, and nothing would stop you reading a card fee off a cash payment. Here the fee only exists where it makes sense.

A match arm names the fields it wants, and inside the arm they’re ordinary names. That’s the only way to get at them, so you can’t read the fee without first having checked that it’s a card.

enum Payment {
    Cash(amount: i32)
    Card(amount: i32, fee: i32)
    Free
}

func charged(p: Payment) -> i32 {
    return match p {
        Payment.Cash(amount) => amount,
        Payment.Card(amount, fee) => amount + fee,
        Payment.Free => 0,
    }
}

A field can be bound under another name, Payment.Cash(amount: a), and one you don’t need can be left out of the pattern.

Your turn: receipt gives “cash 10”, “card 10 + 2 fee” or “free”.

test "receipt" {
    assert receipt(Payment.Cash(amount: 10)) == "cash 10"

    assert receipt(Payment.Free) == "free"

Optionals

Some answers don’t always exist. The first negative number in a list of positive ones; the age of someone you’ve never heard of. Many languages answer with null, or with -1, and the caller has to remember to check. Forget, and the program carries on with a value that isn’t one.

In Rask the type says so: i32? is an i32 or none. You can’t do sums with an i32?, so you can’t forget. You get the number out first:

x ?? 0              the number, or 0 when there's none
if x? as n { }      run the block only when there's a number, as `n`
x is none           true when there's no number

A function returning i32? returns a plain number or none.

func first_negative(numbers: Vec<i32>) -> i32? {
    for n in numbers {
        if n < 0 {
            return n
        }
    }
    return none
}

func describe(numbers: Vec<i32>) -> string {
    if first_negative(numbers)? as n {
        return "starts going wrong at {n}"
    }
    return "all fine"
}

Your turn: step 9’s largest assumed the list wasn’t empty. Make it give none for an empty list instead of crashing.

    todo()
}

test "first negative" {
    assert first_negative(Vec.from([4, -1, -7])) == -1
    assert first_negative(Vec.from([4, 5])) is none
    assert (first_negative(Vec.from([4])) ?? 0) == 0
    assert describe(Vec.from([3, -2])) == "starts going wrong at -2"
}

test "largest" {

Map

A Vec finds things by position. Often you want to find them by name instead: someone’s phone number, a word’s count. Searching a Vec for the name gets slower the longer the list; a Map goes straight to it.

m[key] = value adds or replaces. m[key] reads, and stops the program if the key isn’t there. m.get(key) is the careful read: it gives an optional, none for a missing key, so step 14’s ?? and ? as work on it. m.contains(key) asks whether it’s there.

func phone_book() -> Map<string, string> {
    mut book = Map.new()
    book["Ada"] = "555-0100"
    book["Alan"] = "555-0199"
    return book
}

func number_of(name: string) -> string {
    return phone_book().get(name) ?? "unknown"
}

A Map hands its entries back in no particular order, so don’t rely on one.

Errors are values

Taking money out of an account can fail, and the caller needs to know. Exceptions tell them by jumping out of the function, and nothing in the function’s signature warns that it might. Error codes don’t jump, but they are easy to ignore.

In Rask, a function that can fail says so in its return type: i32 or BankError is either a new balance or a reason. The error is an ordinary value, usually an enum, and the function returns it like any other value.

The caller can’t ignore the result: calling withdraw and dropping what it gives back is a compile error. r is BankError asks which one you got, and r is BankError.NotPositive whether it was that error in particular. if r is BankError as e { } runs the block only for an error, named e, the way ? as does for an optional. r! takes the balance out and stops the program if it’s an error, which is right when an error here could only be a bug.

enum BankError {
    Overdrawn(short: i32)
    TooLarge(over: i32)
    NotPositive
}

func withdraw(balance: i32, amount: i32) -> i32 or BankError {
    if amount > balance {
        return BankError.Overdrawn(short: amount - balance)
    }
    return balance - amount
}

try and catch

Most code that meets an error can’t do anything useful about it, and should hand it to whoever called it. Checking every result by hand with is would bury what the function does under what could go wrong.

try r takes the value out of r, or returns the error from the function you’re in, right there. The function has to be able to return that error, so its own type says or BankError too.

r catch e => fallback deals with the error where it happens instead: it’s the value, or, when r is an error, whatever comes after =>, with the error named e. catch _ => throws the error away, in writing.

enum BankError {
    Overdrawn(short: i32)
}

func withdraw(balance: i32, amount: i32) -> i32 or BankError {
    if amount > balance {
        return BankError.Overdrawn(short: amount - balance)
    }
    return balance - amount
}

func pay_rent_and_food(balance: i32) -> i32 or BankError {
    let after_rent = try withdraw(balance, 700)
    return try withdraw(after_rent, 200)
}

func left_after_rent(balance: i32) -> i32 {
    return withdraw(balance, 700) catch _ => 0
}

Changing what you’re given

Every function so far has only read its parameters. That’s the default, and it’s cheap: a function reads a Vec where the caller keeps it, without copying it. The compiler calls this borrowing, and you’ll see the word in error messages. A borrowed value can’t be changed: a scores.push(1) in a function that only reads scores is a compile error.

So when a function should change the caller’s value, it says mutate, and the caller writes mutate too. You can tell which calls might change your data by reading the calls, without opening every function.

A method that changes its value takes mutate self. There the value it’s called on is the thing being changed, so the call is just p.heal(5).

struct Player {
    name: string
    health: i32
}

extend Player {
    func heal(mutate self, amount: i32) {
        self.health += amount
    }
}

func add_bonus(mutate scores: Vec<i32>, bonus: i32) {
    for i in 0..scores.len() {
        scores[i] += bonus
    }
}

Giving a value away

Sometimes a function keeps what you give it: it puts your list into an order and returns the order. Now two names reach one list, yours and the order’s. If both could change it, editing one would quietly edit the other, and which one cleans the list up when it’s no longer needed?

Rask’s answer is that a value has one owner. A parameter marked take becomes the function’s to keep, and the name you passed in is gone: using it afterwards is a compile error. The compiler calls this a move: the value moved into the function, and the error says “use of moved value”. Small values (numbers, bools, strings, small structs) are copied instead, so this only ever happens to things like a Vec.

This file doesn’t compile. Run rask test 19-take.rk, read the error, and fix summary so it doesn’t use items after giving it away. The compiler suggests a copy; there’s a better fix, since the order has the items now.

struct Order {
    customer: string
    items: Vec<string>
}

func place(customer: string, take items: Vec<string>) -> Order {
    return Order(customer: customer, items: items)
}

func summary(customer: string, count: i32) -> string {
    mut items = Vec.new()
    for _ in 0..count {
        items.push("tea")
    }
    let order = place(customer, items)
    return "{order.customer}: {items.len()} items"
}

Copying on purpose

Copying a list costs time and memory, more the longer it is. Plenty of languages copy behind your back, and a slow program ends up slow in lines that look innocent. Rask never copies anything big unless you ask, and you ask with .clone(), so every copy is there to see.

You need one when you want a changed version of something and the original too. A borrowed parameter can’t be changed (step 18), so to build on it you clone it into a mut name of your own and change that.

func sorted_copy(numbers: Vec<i32>) -> Vec<i32> {
    mut out = numbers.clone()
    out.sort()
    return out
}

Strings are the exception that doesn’t feel like one: they can’t be changed in place, so sharing one is safe and there’s never a reason to clone a string.

Changing an item in a Vec

One change to an item in a Vec is one line: team[i].health -= 3. For several, you’d want a name for the item. But a Player is too big to copy (step 19), so let p = team[i] would be a second name for an item the Vec owns, and a change through either name would change both. That doesn’t compile.

with team[i] as p { ... } names the item where it sits: changing p changes the item in the Vec. While the block runs, the Vec can’t grow or shrink, because a Vec that grows may move its items somewhere else in memory, and p would be left pointing at the old place.

struct Player {
    name: string
    health: i32
    alive: bool
}

func rest(mutate team: Vec<Player>, i: usize) {
    with team[i] as p {
        p.health += 10
        p.alive = true
    }
}

Closures

Counting the even numbers in a list and counting the negative ones are the same loop with a different test inside. Rather than write the loop twice, write it once and take the test as a parameter.

A closure is a small function written where it’s used: |n| n < 0 takes n and gives back whether it’s negative. A parameter that takes one has a function type, func(i32) -> bool. The body can use names from around it, like limit in count_above.

func count_where(numbers: Vec<i32>, keep: func(i32) -> bool) -> i32 {
    mut count = 0
    for n in numbers {
        if keep(n) {
            count += 1
        }
    }
    return count
}

func count_above(numbers: Vec<i32>, limit: i32) -> i32 {
    return count_where(numbers, |n| n > limit)
}

Generic functions

Counting how often 3 appears in a list of numbers and how often “tea” appears in a list of strings is the same code with different types in it. A generic function is written once with a stand-in type, T, and works for each type you call it with.

<T: Equal> says which types are allowed: ones whose values can be compared with ==. The compiler checks the body uses only what the bound allows, so < in here would be an error; that needs Comparable. Numbers, strings, and most of your own structs and enums are both.

Behind the scenes the compiler writes out a copy of the function for each type it’s used with, so a generic function runs as fast as one written for that type by hand.

func count_of<T: Equal>(items: Vec<T>, want: T) -> i32 {
    mut count = 0
    for item in items {
        if item == want {
            count += 1
        }
    }
    return count
}

Interfaces

A generic function can only use what its bound promises. Equal from step 25 is an interface: a list of methods that a type promises to have. Writing your own lets one function work on any type that keeps your promise, like total_area below on squares and rectangles alike.

A type keeps it by saying so, Square implements Shape { ... }, with the methods inside. Having methods with the right names isn’t enough; the compiler wants the words. So a type never takes on a promise by accident, and you can find every shape by searching for implements Shape.

interface Shape {
    func area(self) -> i32
}

struct Square {
    side: i32
}

Square implements Shape {
    func area(self) -> i32 {
        return self.side * self.side
    }
}

func total_area<T: Shape>(shapes: Vec<T>) -> i32 {
    mut total = 0
    for s in shapes {
        total += s.area()
    }
    return total
}

Cleanup that always runs

Some things have to be undone however a function ends: a file closed, a lock let go, a drawer shut. With a return here and a try there, a function has several ways out, and putting the cleanup before each one is easy to get wrong, especially for the exits try makes for you.

ensure says it once, right after the thing it undoes, and runs it when the block it’s in ends, however it ends: a return, an error leaving through try, or simply reaching the }. A call can follow ensure directly, ensure file.close(); anything else goes in braces, ensure { door.open = false }.

struct Till {
    drawer_open: bool
    sales: i32
}

enum PriceError {
    Negative(price: i32)
}

func checked(price: i32) -> i32 or PriceError {
    if price < 0 {
        return PriceError.Negative(price: price)
    }
    return price
}

func refund(mutate till: Till, amount: i32) -> i32 or PriceError {
    till.drawer_open = true
    ensure { till.drawer_open = false }
    return try checked(amount)
}

Racks and links

Some data points at itself: each person in a company has a boss who is another person, rooms in a game lead to other rooms. A struct field can’t hold a borrowed value, and a position in a Vec stops meaning the same person once someone ahead of them leaves.

A Rack holds things that need to point at each other. insert puts one in and gives back a Link, which can be stored in a field. Reading through a link reads the thing it links to: p.boss and p.name work as if p were the Person. In a function that can change the rack, p.boss = ... changes that person. When someone is deleted from the rack, every field that links to them becomes none before the delete returns, so a link to someone who’s gone can’t exist. That’s why boss is a Link<Person>?: the ? is where the none goes, and it makes you check before following the link.

Rack and Link live in the standard library’s memory module. Apart from the basics (numbers, strings, Vec, Map), everything there needs an import line first.

import memory.Rack
import memory.Link

struct Person {
    name: string
    boss: Link<Person>?
}

func chain_of_command(p: Link<Person>) -> string {
    mut text = p.name
    mut next = p.boss
    while next? as boss {
        text = "{text} > {boss.name}"
        next = boss.boss
    }
    return text
}

Tasks and channels

A program often has two things to do that don’t depend on each other: add up two halves of a long list, answer two people at once. Doing them one after the other wastes the time one spends waiting or the second core the machine has.

spawn { ... } starts the block as a task that runs alongside the code that started it. The block is the whole of the task, so it hands back its answer with return, as a function does. join() waits for the task and gives back that answer, or an error if the task crashed, hence the !. Every task you start has to be joined; forgetting one is a compile error. Any function can run in a task, with no special kind of function for it. Tasks need something to run them, which using Multitasking { ... } sets up.

func doubled_and_squared(n: i32) -> i32 {
    using Multitasking {
        let doubled = spawn { return n * 2 }
        let squared = spawn { return n * n }
        return doubled.join()! + squared.join()!
    }
}

A channel carries values from one task to another while both run. Channel<i32>.buffered(10) gives a sending end and a receiving end, which can hold 10 values waiting.

func squares(n: i32) -> Vec<i32> {
    using Multitasking {
        let (tx, rx) = Channel<i32>.buffered(10)
        let worker = spawn {
            for i in 1..=n {
                tx.send(i * i)!
            }
        }
        mut out = Vec.new()
        for _ in 0..n {
            out.push(rx.receive()!)
        }
        worker.join()!
        return out
    }
}

Shared state

A channel hands a value from one task to another. Sometimes several tasks need the same value at once instead: a counter they all add to, a table they all fill in. Two tasks changing one value at the same moment can leave it half of each, and that kind of bug shows up once in a thousand runs. So in Rask a value that more than one task changes has to live in a Shared, which lets one task at a time change it.

with total.write() as n { ... } waits its turn, then gives you the value for the block. A block of one line can follow a colon instead, with total.write() as n: n += 1. .read() instead of .write() only looks, and lets several readers in together. Each task gets its own .clone() of the Shared: a second way to reach the same value, not a copy of it.

total.get() copies a small value out. Anything bigger you clone out of a .read() block, with table.read() as t { return t.clone() }, since the Shared still owns what’s in it.

import sync.Shared

func count_both(times: i32) -> i32 {
    let total = Shared.new(0)
    using Multitasking {
        let mine = total.clone()
        let theirs = total.clone()
        let a = spawn {
            for _ in 0..times {
                with mine.write() as n: n += 1
            }
        }
        let b = spawn {
            for _ in 0..times {
                with theirs.write() as n: n += 1
            }
        }
        a.join()!
        b.join()!
    }
    return total.get()
}

Work done while compiling

Some values never change between runs: a table of squares, the primes under 100. Working them out every time the program starts is wasted effort, and typing them in by hand invites a typo nobody spots.

A comptime block runs while the program is being compiled, and its result is built into the program as a constant. It’s ordinary Rask, and it can call your own functions, as long as they only compute and don’t print, read files or start tasks. const names the result, outside any function.

Design Principles

  1. Safety Without Annotation - Memory safety without lifetime markers
  2. Value Semantics - No hidden sharing or aliasing
  3. No Storable References - References can’t escape scope
  4. Transparent Costs - Major costs visible in code
  5. Local Analysis Only - No whole-program inference
  6. Resource Types - I/O handles must be consumed
  7. Compiler Knowledge is Visible - IDE shows inferred information

Full details: CORE_DESIGN.md

Validation

Rask is validated against test programs that must work naturally:

  1. HTTP JSON API server ✓ (passes type-checking)
  2. grep clone ✓ (implemented)
  3. Text editor with undo ✓ (implemented)
  4. Game loop with entities ✓ (implemented)
  5. Embedded sensor processor ✓ (passes type-checking)

Litmus test: If Rask is longer/noisier than Go for core loops, fix the design.

Metrics

Design decisions are evaluated using concrete metrics:

  • Clone overhead (% of lines with .clone())
  • Graph edge-write cost (nanoseconds)
  • Compile times (seconds per 1000 LOC)
  • Binary size
  • Memory usage

See METRICS.md for the scoring methodology.

Specs and RFCs

Language features are documented as formal specifications in specs/.

Major changes follow an RFC process:

  1. Open an issue for discussion
  2. Draft a specification
  3. Implement in compiler
  4. Validate against litmus tests
  5. Update metrics
  6. Merge if it improves the design

Tradeoffs

Every design has tradeoffs. Rask makes these intentional choices:

  • More .clone() calls - Better than lifetime annotations (our view)
  • An edge write touches the target too - Better than raw pointers with manual tracking
  • No storable references - Simpler mental model, requires restructuring some patterns
  • Explicit costs - Better than hidden complexity

See CORE_DESIGN.md § Tradeoffs for full discussion.

Contributing to Design

When proposing changes:

  1. Explain the problem - What use case is difficult today?
  2. Show the tradeoff - What does this cost?
  3. Test against litmus tests - Does it make real programs better or worse?
  4. Measure the impact - Update relevant metrics
  5. Consider alternatives - What other approaches exist?

The goal is ergonomics without hidden costs. If a feature hides complexity or breaks transparency, it probably doesn’t belong.

Philosophy

“Safety is a property, not an experience.”

Users shouldn’t think about memory safety—they should just write code. The type system and scope rules make unsafe operations impossible by construction.

“If Rask needs 3+ lines where Go needs 1, question the design.”

Ceremony should be minimal. Explicit costs are good; boilerplate is bad.

“Local analysis only.”

Compilation should scale linearly. No whole-program inference, no escape analysis. Function signatures tell the whole story.

How this book is built

Rules for anyone adding a page. They exist because a book is a second copy of the language, and the usual fate of a second copy is to drift until it teaches a version of the language nobody ships.

What a page may contain

Prose, and code that something else already verifies. Nothing else.

You want to showWrite it as
A few lines from a real program{{#include ../path/prog.rk:anchor}}
A small self-contained snippetan inline block with <!-- test: compile --> or <!-- test: run | expected output -->
What a program prints{{#include ../../../../tests/golden/<name>.out}}

<!-- test: parse --> does not count as verified anywhere in the book. Parsing proves the syntax is current; syntax is not what rots. The front-page snippet passed test: parse while calling fs.open, which the real grep program doesn’t use, and missing both its imports, so a reader copying it got two errors on page one. compile type-checks; run | expected runs it and matches the output. Use one of those.

CI runs the markers in its “Docs snippets parse” step, which has covered docs/ for a while. What it can’t tell you is whether a block has a marker at all, or whether the one it has is strong enough, which is what tests/book_gate.sh is for. It also checks that every include resolves: the file is present and the named anchor really is in it, because mdBook renders a missing anchor as nothing at all and says so quietly.

The tour

“Learn the language” is the tour in learn/, one step per idea, and each step is a .rk file the reader runs in a clone: prose in its comments, the idea working, then a todo() for the reader and the test blocks that check it. The pages here are made from those files by learn_pages.py when the book is built, so the text exists once. Comment blocks at the left margin become prose, and the code between them becomes blocks that can be edited and run on the page. A step’s page isn’t committed; don’t write one by hand.

tests/tour_gate.sh holds the steps to what they promise: each one fails as shipped, and its answer in learn/solutions/ passes on both backends. Each step declares the idea it introduces with a // new: <idea> line, and tests/tour_ideas.py knows what each idea looks like in code, so a step that uses something a later step teaches fails the gate. That was the old tutorial’s worst problem: a chapter’s exercise needed the next chapter.

A new step goes in the order, with a solution, a // new: line, an entry in tour_ideas.py, and a line in SUMMARY.md and learn/README.md. learn_pages.py fails the build when either list disagrees with the files.

How to explain it

The machine is the metaphor. Describe what actually happens in memory, in plain words, and don’t build a story on top of it.

Lending is the cautionary case. In a library the book leaves the shelf; in Rask the caller goes on reading the value for the whole call. A reader who builds the library model predicts the wrong thing at their first mutate call — and learned it here.

Rask can afford the literal route where most languages can’t. No lifetime annotations, no reference type, no effects: every rule is a claim about bytes and where they sit. So make the claim.

One noun carries it: storage. A place in memory holding a value. A name reaches storage, a move hands it over, a borrow reads storage the function doesn’t own, a copy makes a second one. Define it once and don’t introduce a parallel vocabulary three chapters later.

Idea first, word second. Build the model in plain language, then attach the term in one sentence, as a hook for the error messages:

A function that takes a value without take reads the caller’s storage where it sits — it doesn’t get a copy, and it doesn’t get to keep it. The compiler calls this borrowing, and you’ll see the word in error messages.

Jargon is a label for something the reader already has. Arriving before the idea is what makes a language feel like it was written for people who already know it.

Spend a metaphor only where the literal thing isn’t observable. In Rask that’s almost nowhere, which is the design working rather than a style choice. Every spend should feel like a defeat.

The test for a paragraph: could a reader predict the next error message from what it just told them? If they’d have to re-derive it from a metaphor first, the paragraph is doing the wrong job.

No “I”, and no decisions. The style guide keeps first person for design writing, where someone is owning a tradeoff. A chapter isn’t that. It explains a language that already works, to someone trying to use it, so it says what the rule is and why it holds: “taking a lock is a real cost, so it belongs in the source where it happens”, never “I picked scoped access over making a shared value feel like a plain one”. Same reasoning, no author in the room.

The difference from the section below is worth keeping straight. The why belongs in a chapter. The choosing doesn’t: alternatives that were weighed, what was rejected and what it would have cost are design writing, and they live in specs/ and RULINGS.md. A reader learning Shared needs the reason the lock is visible. They don’t need to know it was ever up for debate.

Write the language, not the compiler’s current mood

A chapter describes the language as it’s designed. A bug in one backend is a bug, not a smaller language, and it never decides what a page is allowed to teach.

When the two backends disagree the interpreter is the reference, so a block that runs correctly there is correct. Mark it <!-- test: run-interp | expected -->, which exists for this, and file the native gap. The block stays verified, the chapter stays honest, and the marker is what the fix later deletes.

What this rules out is quietly teaching less. The scoped-access chapter dropped recursive Heap for a day because the recursive case doesn’t lower on native (#1234), and what the page taught instead was a smaller language that happens to match one backend’s bugs. A reader can’t tell the difference between “Rask doesn’t do this” and “Rask does this and the compiler is behind”, and only one of those is true.

Caveats about what’s broken don’t belong in a chapter either. They date instantly and they’re the issue tracker’s job.

The book teaches the ruling, not just the rule

The specs are normative and say what the rule is. A chapter’s job is the part the spec tables leave out: why it holds. “The marker is required” is a spec line. “A misread move is caught for you and a misread mutation isn’t, so the one that can’t be caught is the one you write down” is a chapter.

Note what that example doesn’t do: it never mentions the alternative, or that anyone chose. It gives the reader the reason and stops. That’s the line between a why, which belongs here, and a decision, which belongs in specs/.

specs/RULINGS.md is where those arguments come from. If a chapter can’t say why, it’s restating the spec and should link to it instead.

Size is capped by the language, not by the author

specs/DAY_ONE.md holds the reading set: the concepts you need to read someone else’s Rask, which must fit one page. The guide inherits that budget: roughly one chapter per Day-One concept, and no chapter for something that isn’t in the language yet.

This is the answer to books that grow to a thousand pages: the guide can’t outgrow the language, because its table of contents is the language’s own list. Anything deeper goes to specs/, which is allowed to be long.

What to do when the language changes

Nothing, usually. That’s the point: included code moves with its program, a tour step fails its gate when the compiler stops agreeing with it, program output comes from the goldens. The prose only needs touching when a decision changes, which is rare and deliberate.

If you find yourself keeping a page in step by hand, the page is built wrong.
