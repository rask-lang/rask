A race, caught and replayed

Two transfers leave one account at the same time. Every read and write of the balance holds the lock, so there is no data race. The test still fails about one run in eight. This page finds the failing run, replays it from a single number, and shows you what each task did.

The bank

Alice has 100. One task sends 80 to Bob, another sends 80 to Carol. Only one of them should get through.

The balances live in a Shared, and the only way into one is a with block that holds its lock. That rules out two tasks touching balances at once. It says nothing about the gap between two blocks, and transfer checks the balance in one and debits it in the next.

Run it the usual way

It passes. Run it two hundred times on a four-core machine and it fails about twenty-five of them, each time on whatever interleaving the hardware happened to pick. By the time you look, that interleaving is gone.

Run it under sim

With --sim the program runs on one OS thread, and every decision the hardware used to make comes from a seed instead: which task runs next, where a running task gets cut off, what the clock says. The scheduler, the run queues and the work stealing are the ones that ship. Only the choices are drawn from the seed.

The same seed takes the same path every time, so a failure comes with the command that brings it back. Seeds 1, 2 and 3 all fail. Of the first hundred, 43 do.

Watch it happen

Add --trace bank.json to that replay line and sim writes down what every task did at every step: each lock it took, each line it printed, when it started and finished. This is that file, drawn one task to a column.

read bank a read that went stale before its task wrote, and that write

The fix

The check and the debit go in one block, so no other transfer can land between them. Two thousand seeds pass.

What this is

Deterministic simulation is how FoundationDB and TigerBeetle earn trust in their concurrent code. Each built its own. In Rask it's part of the test runner: the same program, linked against a runtime that takes its orders from a seed.

Beyond scheduling, sim runs a virtual clock (a 30-day sleep takes no wall time), keeps file writes in an overlay, and can inject I/O errors, dropped connections and clock jumps when a test asks for them. The rules are in the sim spec. The programs and traces on this page are the files next to it, and a test in the compiler's suite regenerates the traces and fails if they change.
